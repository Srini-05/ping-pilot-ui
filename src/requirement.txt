# Build a Modern Bulk Ping Test Web Application

Build a production-quality internal web application called **Bulk Ping Test** that provides a modern, highly usable UI on top of an existing Python `bulk_ping.py` ping-testing script.

The goal is to replace the current manual workflow:

```text
Create devices.txt
        ↓
Copy bulk_ping.py
        ↓
Run:
python3 bulk_ping.py -f devices.txt
        ↓
Wait for execution
        ↓
Read ping_results_YYYYMMDD_HHMMSS.txt
```

with a simple web UI:

```text
Upload / Paste / Import
        ↓
Extract device/IP/hostname values
        ↓
Review & Clean
        ↓
Start Ping Test
        ↓
Live Progress
        ↓
Results Dashboard
        ↓
Download Report
```

Users must be able to provide the list of devices to ping in multiple ways.


This is one of the most important features.

NEVER immediately start pinging after importing a file.

Always take the user to a **Review Devices** stage.

Example:


# 4. Smart Parsing

Create a parser that identifies:

### IPv4

Example:

```text
10.10.10.1
192.168.1.100
172.16.0.10
```

### IPv6

Support IPv6 if the existing backend supports it.

### Hostnames

Example:

```text
server01.company.com
prod-db-01.company.local
web01
```

The parser should normalize:

```text
10.10.10.1,
10.10.10.2;
10.10.10.3

10.10.10.4
```

into:

```text
10.10.10.1
10.10.10.2
10.10.10.3
10.10.10.4
```

Trim whitespace.

Remove empty lines.

Detect duplicates.

Do not silently discard suspicious values. Show them in the review screen.

# 27. Security

Because this is an internal network tool:

* Validate all uploaded files
* Limit file sizes
* Validate file types
* Sanitize extracted text
* Never execute uploaded files
* Never treat uploaded content as executable code
* Validate device targets on the backend
* Prevent arbitrary OS command injection
* Never directly concatenate user input into shell commands
* Use safe subprocess execution
* Authenticate the application if deployed internally
* Log test execution
* Do not expose backend filesystem paths to users
* Do not expose server secrets/API keys to frontend code

# 31. Technology Flexibility

If a simpler deployment is preferred, a plain HTML/CSS/JavaScript frontend is acceptable.

However, the UI must still communicate with the Python backend through HTTP/SSE/WebSocket.

Do not try to execute the Python ping script directly inside the browser.

The browser cannot safely execute the server's Python/OS ping functionality.

---

# 32. No Database — Initial Version

The first version should work WITHOUT a database.

The architecture should be:

```text
Browser
   ↓
Frontend
   ↓
FastAPI
   ↓
Python Ping Service
   ↓
Operating System
   ↓
Ping
```

Temporary test state can live in backend memory while the test is running.

Reports can be generated as files for download.

Do NOT introduce PostgreSQL/Supabase/etc. unless specifically required.

However, design the service layer so a database can be added later.

# 34. Important Backend Constraint

The existing Python ping behavior is the source of truth.

Before implementing UI assumptions, inspect the actual `bulk_ping.py`.

Determine:

* How ping is executed
* Supported OS
* Timeout behavior
* Number of packets
* Concurrent execution
* Retry logic
* Output format
* Error handling
* IPv4 support
* IPv6 support
* Hostname support
* Exit codes
* Current report format

Do not invent functionality that the script does not currently support.

If improvements are necessary, clearly separate:

```text
Existing functionality
```

from:

```text
New UI/backend functionality
```
